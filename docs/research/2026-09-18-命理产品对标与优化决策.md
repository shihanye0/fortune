# 命理产品对标与本轮优化决策

> 调研日期：2026-09-18  
> 范围：个人化八字/日运势/占卜 Web 产品；不把“预测效果”视为可验证的产品指标。

## 结论

本项目的功能广度已经覆盖每日运势、六爻、奇门、推送和反馈；相较成熟产品，短板不首先是再堆一个术数入口，而是三个可感知的基础能力：**排盘口径准确、结论可核对、使用边界清晰**。本轮优先修复这三项，而没有直接复制合婚、起名、付费咨询或社区等重运营功能。

## 本项目发现

| 项目 | 发现 | 风险 |
| --- | --- | --- |
| 四柱计算 | 原实现直接读取农历年/月干支，未使用依赖库的 `EightChar` 精确节气口径。 | 立春附近可能按农历年而非节气年排盘。 |
| 大运 | 原实现强制 `10、20、…` 岁起运。 | 起运年龄和年份不可核对，专业可信度低。 |
| 五行偏向 | 原实现只统计四柱天干，且日主偏弱时把“我生”的五行误当作“生我”。 | 日运评分的基础数据不足且方向可能相反。 |
| 个人中心 | 已有排盘引擎，但用户仅能看阳历/农历生日，无法核对四柱、五行或大运。 | 用户只能相信总分和 AI 文本，无法判断计算来源。 |
| 时间精度 | 前端曾提供“分”选择，但后端并未保存或计算分钟。 | 形成虚假的精度承诺。 |

## 本轮已落地

1. `calculate_bazi` 改为通过 `lunar-python` 的 `EightChar` 计算精确四柱：年、月按节气（含立春），日柱采用库的默认零点换日口径。
2. 大运改为使用库的节气差起运结果，返回起止年龄和年份区间；不再固定从十岁开始。
3. 五行统计改为四柱天干、地支八个可见字；基础偏向规则修正“生我/我生”的方向错误，并在接口中说明它不包含藏干、月令和格局权重。
4. 新增认证接口 `GET /api/v1/users/me/bazi-profile`，个人中心提供四柱、十神、五行条形分布、大运区间、计算口径和使用提示。
5. 移除了无法持久化的“分钟”编辑控件；首页从“精准”承诺改为“传统文化参考”，并明确不用于医疗、法律、投资等重要决策。

## 本次推送与评分方案

### 已确认根因

- 日运计算层原生输出为 **1--5 分**，但网页、邮件和飞书使用了 **50/70/90 或 60/80 分** 阈值，因此 1--5 分都会被显示成“平”或低等级。
- 异常降级分支曾写入 60 分及 description 字段，与正常日运的 1--5 分及 detail 字段不一致。
- MiMo 的旧 Token Plan 地址和旧参数同时存在于界面、文档、测试连接与正式请求中；两条请求链不一致，无法从一次测试连接推断实际推送解读可用。

### 落地决策

1. 保持数据库和计算层的 1--5 分合同，不进行高风险的全库分制迁移；读取历史百分制异常记录时兼容归一化。
2. 全渠道统一展示为：1 宜守、2 谨慎、3 平、4 偏吉、5 顺势；分数始终带 /5，不再把 1--5 当百分制。
3. 邮件采用“日运简报”：综合状态、四维卡片、幸运信息、解读、少量重点时段和纯文本备份；动态内容做 HTML 转义。
4. 服务器默认回到 DeepSeek；用户自定义的 MiMo 等 OpenAI 兼容地址继续保留其参数适配。个人覆盖与服务器默认在设置页中明确区分，避免误以为“留空”会自动覆盖已保存 Key。
5. 测试连接与正式解读共用同一请求封装。没有可用回复时显示真实的配置/配额提示，不伪造“连接成功”。

## 不建议现在做

- 直接复制合婚、起名、咨询、祈福或社区：这会引入运营、内容审核、支付和合规范围，不能靠当前单体项目安全验证。
- 声称“真太阳时”“精准预测”或把基础五行统计称为完整喜用神：现有输入、模型和验证证据不足。
- 让 LLM 自行计算干支或大运：应保持确定性排盘与生成式解释分层。
